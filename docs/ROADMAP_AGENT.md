# VelvetDesk AI — шлюз, лицензии, синхронизация

Рабочий план коммерческой части: платный шлюз к LLM, лицензирование клиента и
синхронизация базы между устройствами оператора. Документ описывает решения и
их причины; порядок работ — в разделе «Этапы».

---

## 0. Что уже есть в клиенте

Прежде чем писать новое, стоит знать, что половина «шлюза» уже живёт в
десктопе и переносится копированием логики, а не переписыванием:

| Что | Где | Состояние |
| --- | --- | --- |
| Пул ключей, round-robin, кулдауны по вердиктам (`RateLimited` 60 с, `QuotaOrAuth` 900 с, `ServerError` 15 с, `Transient` 5 с, `Fatal`/`Blocked` без ожидания) | `src-tauri/src/llm/keypool.rs` | готово |
| Падение на следующую модель провайдера | `src-tauri/src/llm/catalog.rs`, `mod.rs` | готово |
| Провайдеры Gemini / OpenAI-совместимые (в т.ч. NVIDIA, OpenRouter) | `src-tauri/src/llm/{gemini,openai}.rs` | готово |
| `updated_at: DateTime<Utc>` у `Profile`, `Man`, `ChatThread` | `src-tauri/src/models.rs` | готово |
| Ключи оператора вне настроек, отдельным файлом | `Secrets` → `secrets.json` | готово |
| Кеширование промпта | — | нет, см. §4 |
| Лицензии, шлюз, синхронизация | — | нет |

## 1. Ограничение, которое надо решить до кода

Пул **бесплатных** ключей Gemini под платную подписку — нарушение условий
Google API: бесплатный тариф не предназначен для перепродажи, а массовая
регистрация проектов под ключи ведёт к бану всей связки разом, а не по одному
ключу. Технически ротация работает; коммерчески это мина под сервис, у
которого уже есть платящие люди.

Тот же код ротации работает и без этого риска:

- **платные ключи в пуле** — ротация нужна не ради лимитов, а ради
  устойчивости (кулдаун при 429, отвал ключа при 401);
- **OpenRouter / DeepSeek с оплаченным балансом** — один ключ, цена по
  токенам, лимит выставляется на стороне шлюза (§3.5);
- **BYOK остаётся бесплатным тарифом** — оператор приносит свой ключ, шлюз не
  участвует.

Далее «пул ключей» означает пул оплаченных ключей.

## 3. Шлюз (`server-gateway`)

### 3.1 Стек

Python отпадает по решению. Остаются два варианта, и они различаются не вкусом,
а тем, куда их можно выложить:

| | TypeScript на Hono (Bun локально) | Rust на axum |
| --- | --- | --- |
| Vercel | штатно, Node-рантайм, стриминг поддержан | только community-рантайм, для продакшена не годится |
| Cloudflare Workers | штатно | через WASM, с обрезанным I/O |
| Fly.io / Railway / VPS | штатно | штатно |
| Переиспользование `keypool.rs` | нет, ~240 строк переписать на TS | да, общим крейтом |
| Хранилище | SQLite через `bun:sqlite` на VPS, Turso/libSQL в serverless | SQLite файлом, serverless отпадает |

**Выбор: TypeScript + Hono.** Причина ровно одна и она практическая: «пропихнуть
на условный Vercel» получается сразу и без экзотики, тот же код запускается
`bun run` на любом VPS, а Cloudflare Workers остаются запасным аэродромом.
Потеря — переписанные 240 строк пула ключей; это полдня, а не неделя, и логика
уже описана вердиктами и кулдаунами, копировать надо поведение, а не строки.

Rust стоит брать, только если шлюз переезжает на свой VPS насовсем и хочется
один крейт на клиент и сервер. Тогда — axum на Fly.io, но Vercel из уравнения
уходит.

**Важно про serverless:** локального файла SQLite там нет — диск не переживает
запрос. Для Vercel-теста база едет в Turso (libSQL, протокол тот же SQL, драйвер
меняется одной строкой) или Neon. На VPS — `bun:sqlite` файлом. Слой доступа к
данным писать за интерфейсом, чтобы смена не расползлась по коду.

### 3.2 Контракт с клиентом

- `Authorization: Bearer <VD-LICENSE-KEY>`;
- эндпоинты, совместимые с тем, что клиент уже умеет: OpenAI-совместимый
  `/v1/chat/completions` и нативный Gemini
  `/v1beta/models/<model>:{generateContent,streamGenerateContent}`;
- стриминг `text/event-stream` сквозной, без буферизации ответа целиком
  (Hono: `streamSSE`, апстрим пробрасывается телом, а не собирается в строку);
- заголовки ответа `X-VD-Credits-Left`, `X-VD-Window-Reset` — клиенту есть что
  показать оператору до того, как тот упрётся в лимит.

### 3.3 Ротация и привязка ключа к диалогу

Ротация round-robin **на каждый запрос ломает кеш провайдера** (§4): кеш
привязан к ключу/проекту, и следующий запрос того же диалога с другого ключа
считается новым префиксом — по полной цене. Поэтому:

- ключ выбирается **липко**: `key = pool[hash(license_id, thread_id) % len]`;
- ротация включается только по вердикту (`RateLimited`, `QuotaOrAuth`,
  `ServerError`, `Transient`) — как в `keypool.rs`;
- после отвала диалог остаётся на новом ключе до конца окна кеша и назад не
  возвращается — иначе кеш теряется дважды.

### 3.4 Состояние пула в serverless

На Vercel процесс не живёт между запросами, а значит кулдауны в памяти
испаряются. Состояние ключей (`cooldown_until`, `failures`) кладётся в ту же
базу, что и счётчики, а в памяти держится только кеш на время запроса. На VPS
это лишняя запись; на serverless — единственный способ, чтобы пул вообще
работал. Один слой доступа, две реализации не нужны.

### 3.5 Лимиты и окупаемость

Считать запросы бессмысленно: запрос с досье на 12 тысяч токенов и «привет»
стоят по-разному. Единица учёта — **кредит**, нормированный по цене:

```
credits = (in_tokens_uncached * price_in
        + in_tokens_cached   * price_cached
        + out_tokens         * price_out) / credit_rate
```

`price_*` берутся из таблицы моделей в базе (правится без пересборки),
`credit_rate` подбирается так, чтобы 1000 кредитов равнялись фиксированной
сумме себестоимости. Тогда маржа считается арифметикой, а не на глаз.

Окна, оба одновременно:

- **скользящее 5-часовое** — режет всплеск (оператор в смене), не наказывая за
  активный день;
- **недельное** — режет себестоимость месяца.

Реализация: таблица `usage(license_id, ts, credits, model)`, лимит проверяется
суммой за окно перед запросом и дописывается после ответа фактическим расходом
из `usage`-полей апстрима. Отказ — `429` с телом
`{ "reason": "window", "reset_at": ... }`; клиент показывает срок, а не ошибку.

Потолки хранятся в лицензии (`tier`), а не хардкодом.

### 3.6 Модели

Стартовый набор: DeepSeek (дёшев, кеш автоматический), Qwen через OpenRouter,
Gemini Flash. Порядок падения — тот же, что в `catalog.rs`.

## 4. Кеширование промпта

Кеш даёт основной выигрыш именно здесь: системный промпт, досье мужчины и
история диалога повторяются в каждом запросе смены почти без изменений.

| Провайдер | Механика | Что делать |
| --- | --- | --- |
| DeepSeek | автоматический disk cache, попадание дешевле | ничего, кроме стабильного префикса |
| Gemini 2.5 | implicit caching автоматически; explicit (`CachedContent`, TTL) — с порогом по токенам | стабильный префикс; explicit только для длинных досье |
| Anthropic через OpenRouter | явные точки `cache_control` | ставить точку после досье |
| Qwen и прочие через OpenRouter | зависит от апстрима, кеш проксируется | сверять по `usage` в ответе |

Единственное архитектурное требование ко всем: **порядок сообщений от
стабильного к изменчивому** — системный промпт, затем досье и факты, затем
история, и только в конце новое сообщение мужчины. Любая вставка изменчивого
(время, счётчики, случайные подсказки) в начало обнуляет кеш целиком.

Проверка, что кеш работает: логировать `cached_tokens` из `usage` ответа и
выводить долю попаданий в статистику шлюза. Без этого «мы включили кеш»
недоказуемо.

## 5. Лицензии

- ключ подписывается сервером Ed25519, клиент проверяет подпись локально —
  офлайн-запуск не ломается при пропаже сети;
- полезная нагрузка:

```json
{
  "license_id": "VD-PRO-XXXX-YYYY",
  "tier": "pro",
  "expires_at": 1790000000,
  "max_peers": 2
}
```

- хранится рядом с ключами (`secrets.json`, права 600), в настройки не попадает
  и не синхронизируется;
- в клиенте — провайдер `velvetdesk_cloud` рядом с существующими, так что весь
  путь вызова (`llm::mod`) остаётся прежним;
- UI: в модалке ключей переключатель BYOK / VelvetDesk Cloud, поле `VD-…`,
  статус подписки, остаток кредитов из заголовков ответа.

## 6. Синхронизация устройств

### 6.1 Транспорт

Прямой IP:порт не годится: операторы за NAT и на мобильном интернете, белого
адреса нет. WebRTC DataChannel + публичный STUN (`stun:stun.l.google.com:19302`)
пробивает большинство NAT; сигналинг — WebSocket на шлюзе, полезная нагрузка
меньше килобайта. Для симметричных NAT нужен фолбэк: TURN дорог по трафику,
поэтому проще E2EE-релей на том же шлюзе (шифротекст, сервер не видит
содержимого). На Vercel WebSocket не живёт — сигналинг и релей уезжают на VPS
или Cloudflare Durable Objects; для теста шлюза это не блокер, части независимы.

### 6.2 Спаривание

1. Устройство А выпускает одноразовый инвайт-код (id пира + сессионный ключ).
2. Устройство Б вводит код в «Синхронизация → Подключить устройство».
3. Обмен SDP/ICE через сигналинг, дальше — прямой канал.

### 6.3 Данные

- синхронизируются `profiles/`, `men/`, `chats/`; `settings.json` и
  `secrets.json` — никогда;
- обмен картой версий `{ id: updated_at }`, поле уже есть в моделях;
- конфликт — LWW по `updated_at`, проигравшая версия уезжает в
  `app_data/backups/conflict_<ts>/`, а не стирается;
- принятые данные проходят `doctor` до записи и пишутся атомарно
  (`.tmp` + rename), как весь остальной storage;
- при обрыве изменения копятся в `sync_queue.json` и уходят следующим
  рукопожатием.

Осторожно с LWW по стенным часам: у двух машин время расходится. Хранить рядом
счётчик правок (`rev`), сравнивать сначала его, `updated_at` — разрешение
ничьей.

## 7. Этапы

### Этап 1 — шлюз
- [ ] `server-gateway` на Hono: OpenAI- и Gemini-совместимые эндпоинты, SSE
      сквозным потоком;
- [ ] пул ключей на TS: вердикты и кулдауны по образцу `keypool.rs`, состояние
      в базе (§3.4);
- [ ] липкий выбор ключа по `(license_id, thread_id)`, ротация по вердикту;
- [ ] слой данных за интерфейсом: `bun:sqlite` на VPS, Turso в serverless;
- [ ] таблицы: лицензии, цены моделей, `usage`;
- [ ] кредиты, окна 5 ч и неделя, заголовки остатка;
- [ ] лог `cached_tokens` и доля попаданий кеша;
- [ ] деплой-тест на Vercel: стриминг не буферизуется, холодный старт не
      теряет кулдауны.

### Этап 2 — клиент
- [ ] провайдер `velvetdesk_cloud`, заголовок лицензии;
- [ ] проверка подписи Ed25519 в ядре, хранение в `secrets.json`;
- [ ] порядок сообщений «стабильное → изменчивое» в сборке промпта;
- [ ] UI: переключатель BYOK / Cloud, ввод ключа, остаток кредитов;
- [ ] тесты: истёкшая лицензия, отказ по окну, восстановление после 429.

### Этап 3 — синхронизация
- [ ] `rev` рядом с `updated_at` в `Profile`, `Man`, `ChatThread`;
- [ ] `sync::engine`: дайджест версий, дельты, очередь;
- [ ] транспорт: DataChannel + E2EE-релей как фолбэк (VPS, не Vercel);
- [ ] спаривание и лимит `max_peers` из лицензии;
- [ ] тест: А правит факт о мужчине → Б применяет патч без потери целостности;
- [ ] тест: конфликт двух правок → проигравшая в `backups/conflict_*`.

## 8. Безопасность

1. Сессионный ключ пары шифрует весь P2P-трафик; сигналинг и релей видят только
   шифротекст.
2. Ключи провайдеров живут на шлюзе и не покидают его; клиент их не получает
   даже в маскированном виде.
3. `secrets.json` не синхронизируется и не попадает в бэкапы синхронизации.
4. Лицензия проверяется подписью, а не ответом сервера: подмена DNS не даёт
   доступа к шлюзу, потому что доступ даёт ключ в заголовке, а не проверка.
